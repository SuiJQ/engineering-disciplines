# 接线类缺陷只能靠「从外部观察真实装配根」的判据抓到

**Trigger**：某参数、端口、模块在装配链中途被丢弃——上层收了不用、零件完整却零引用、值被读了只用于本地计算而不往下传；此时**所有既有测试全绿**，且手工直传目标件的判据也全绿。

**核心判据**：绿的原因是测试从内部绕过装配点直接手工接线。判据必须分两层，第二层不可省：手工直传只能证明「传了参数就生效」，证明不了「装配根传了」——而这类缺陷恰恰出在装配根，所以单层判据连自己都骗。

## Steps

1. **列出装配链上每一环的「读了没有 / 传了没有」**：把端口签名、模块成员、被读到的配置值逐一对照到最终消费者，找出断在哪一跳。
2. **写第①层判据**：手工把参数直传目标件，断言下游行为改变。它只锁定「参数一旦送达就生效」，是必要的单件回归保护。
3. **写第②层判据**：走真实装配根全程（装配根须可注入），**只断言编排器实际发出的请求 / 落盘产物**，内部怎么拼一律不查。
4. **证伪分两层分别做**：删掉修复行后，观察第②层红而第①层仍绿——这个差值本身就是「缺陷位于装配根」的证据，也是两层判据都值得存在的理由。
5. **还原后必须重跑全量**，并确认备份拍在改动之前（见 Failure modes）。
6. **把「全绿」当异常信号处理**：这类同型缺陷反复以「所有测试绿」出现，绿不是通过的证据而是要换观察层的信号。

## Pre-conditions / inputs

- 装配根可注入（否则第②层退化成真跑，成本与副作用上升）
- 下游可从外部观测：发出的请求、落盘产物、返回结构三者之一
- 已知断点在哪一跳（第 1 步的对照表）

## Failure modes / caveats

- **手工直传的判据会给出虚假的安心感**：证伪时它仍全绿，因为它亲手补上了缺失的那一跳。
- **只断言结构而非行为同样抓不到**：查函数返回值、查参数存在性都可能被不同实现满足，须落到实际发出的数据。
- **局部测试集可能掩盖跨组缺陷**：只有全部一起跑才炸的单例存在，因此还原后的验证必须是全量。
- **备份拍在改动之后 = 还原等于撤掉修复**：证伪前先拍改动前版本，还原后重跑全量确认修复仍在（与 把不变量写成会红的断言，并验证断言本身 中「先确认判据能正确失败」是同一条纪律的两面）。
- 测试夹具自身可能少传参数而使判据空转；helper 的返回类型标成宽类型会让类型检查器另冒一批错，掩盖真问题。
- 这类缺陷与「文档声称 A、代码做 B」「路径组合在数百条绿测试下存活」同源，判据设计的底层依据见 审计的主要工作量在核对承诺，不在读代码；另一种「全绿即危险」的独立形态见 只测 ASCII 的测试在中文语境下必然假绿。

## Sources

- 判据分两层、以及证伪时「第②层红、第①层仍绿」的关键差值，见 政通-harness 项目日记（2026-10-02 D-231 容量接线修复）：其中记录装配根读了配置容量却只用它算预算、没把容量传给下游，故三种容量配置下压缩触发线完全相同；判据因此特意做成手工传参与走真实装配根两层，删掉修复行时恰是装配根那两条红。
- 「本项目第五次同型缺口、共同特征是所有既有测试全绿、只能靠从外部观察实际行为的新判据抓到」的判断，同样由该日记给出：先前几次分别是端口收而不读、零件完整却零引用、模块整体未接线、性质定义了却无人查。
- 当日进度条目 2026-10-02 日记 复述了同一轮的结论与执行坑：证伪备份取自改动前版本导致还原不完整、修复被一并撤掉，须重新应用并重跑全量后才提交。
