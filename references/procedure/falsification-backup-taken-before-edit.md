# 证伪前拍改动前备份，还原后重跑全量

**Trigger**：准备做证伪（临时删掉/改坏刚写的那处实现，看判据是否变红），准备随手 `cp` 一份当前文件当备份。

**核心判据**：备份的作用是「回到改动前的状态以验证判据能红」，不是「回到改动后的状态以收工」。拍在改动之后的备份会同时撤掉修复，而这类二次事故不会自己暴露——还原后如果只跑新增的那几条判据，看起来一切正常。

## Steps

1. **先备份，再动手**：在改第一行之前把待改文件复制出去（或用 `git stash`/`worktree` 留一份干净基线），命名上标明它是改动前版本。
2. **写判据、确认红**：先有判据再改实现；见 接线类缺陷只能靠「从外部观察真实装配根」的判据抓到 中判据分两层的做法。
3. **跑全量，确认缺陷坐实**（不是只跑新增判据）。
4. **施加改动**，再跑全量 + lint + 类型检查，把三类问题一次清干净。
5. **证伪**：撤掉改动 → 跑判据确认红（红的条数与预期一致才算数）。
6. **还原**：从步骤 1 的备份恢复，**然后无条件重跑全量测试 + 类型检查**，两者都绿才允许提交。
7. **写决策、提交**，记录本轮判据条数与提交号。

## Pre-conditions / inputs

- 改动前的干净基线（备份或 VCS 基线）
- 一条可跑的判据（否则第 5 步无从确认「该红」）
- 全量测试与类型检查命令（局部绿不算数）

## Failure modes / caveats

- **备份拍晚了 = 还原即撤修复**：这是本流程唯一会直接造成二次事故的错误，症状是「还原后修复消失但没报错」。
- **「改动很小所以不重跑全量」是假的省事**：只跑新增判据会漏掉把修复撤掉这件事本身；全量是唯一能发现还原不完整的检查。
- **局部绿掩盖跨组缺陷**：有只在全部一起跑才炸的单例，全量是硬要求。
- **同族执行坑**：冻结 dataclass 在判据里只能经构造参数改值，赋值会报错；自建测试 helper 的返回类型若标成宽类型，lint 自动修完后类型检查会再冒一批 error，掩盖真问题。
- 判据本身要能正确失败，这是与 把不变量写成会红的断言，并验证断言本身 共用的前置纪律；审计层面的呼应见 审计的主要工作量在核对承诺，不在读代码。
