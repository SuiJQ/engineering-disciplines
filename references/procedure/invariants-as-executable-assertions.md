# 规则不写成文档，而是写成会红的断言

**Trigger**：发现自己在往 README / 架构文档 / 规范里写「必须」「禁止」「不得」这类靠人自觉的规则——尤其是依赖方向、构造边界、文档与实现同步这类功能测试抓不住的退化。

**核心判据**：文档里让人自觉的规则三个月内必然失效，评审也抓不住；唯一可靠形态是会红的断言，且**判据自身也要被判据覆盖与验证**。

## Steps

1. **逐条挑出不变量**，按退化形态选断言手段：依赖方向与构造边界用 `ast` 断言（不是 import 检查）；文档表格 / 事件表与代码同步，用**读权威原文**的测试（读转述会与原文一起腐化）。
2. **断言「谁能构造对象」而非只断言「谁能 import」**，否则合法 import 后仍可 `new`，注入可被绕过。
3. **把检查器的 include 范围扩到判据代码自身**（测试目录、断言脚本）；判据不受检查是配置漏洞，不是小事。
4. **先确认判据能正确失败**：塞坏输入 / 改一个名字，看它是否真的红。全绿输出不等于被检查过。
5. **误杀合法数据时改规则，不加豁免**——误杀的规则会逼人写 noqa 绕过，那是真损失。
6. **把声明范围收窄到已存在的行为**，不去测尚未实现的阶段，否则判据会长期空转。

## Pre-conditions / inputs

- 该规则的具体退化形态（依赖方向 / 对象构造 / 文档同步 / 范围收敛）
- 权威原文的位置（供「读原文」型断言取源）

## Failure modes / caveats

- 判据自己写坏时会给出一批误报，误报让人开始忽略红，此时应先质疑尺子（见 审计的主要工作量在核对承诺，不在读代码 中「坏尺子要先证伪」的同源教训）。
- 断言「注入齐全」不等于「被使用」：假实现齐备仍可能是管线通通的假象，必须在流程里复验它真被调用。
- 只锁已实现行为时，后续新增阶段要主动扩范围，否则断言静默覆盖不到——与 把承诺压缩成「一句话 + 立刻写出文件」的绑定动作 中「范围判据须前置声明」是同一条纪律。

## Sources

- 这一流程及其四条附加原则见 政通项目设计冻结纪要：其中记录把依赖规则落成 `ast` 断言（违反即 CI 红）、新增读架构原文的同步测试（故意改一个事件名即被抓出）、把类型检查范围从 `src` 扩到含 `tests` 后立刻暴露多处报错，以及「误杀的规则会逼人给每个对象加 noqa 绕过，那才是真损失」的判断。
- 同一纪要补充了「判据要读窄」的配套教训：八个端口全部构造注入看起来齐了，实际流程里只真调用了两个，因此需要把复验层从「已注入」下移到「流程中确实被调用」；反向的纪律——只锁已存在的序列化确定性、不去测尚未实现的导出器阶段——同见该文件。
- 跨项层面的呼应见 当日项目纪要：其中把「文档声称存在的测试其实根本不存在」列为空承诺，并把审计主要工作量定位为核对承诺本身。
