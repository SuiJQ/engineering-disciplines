# 大文件改动的事故恢复纪律

**Trigger**：要做「把方法/代码从一个位置搬到另一个位置」的结构性搬移，或对整个文件做正则批量改写（async 化、批量重命名等）——单次动作的影响面就覆盖大量行。

**核心纪律**：这类改动的回退粒度只能是「动过的那几行」，不能是「整个文件」。

## Steps

1. **先整份备份，再动第一行**：把待改文件原样拷到包外（如 `/tmp/backup.py`）。这是事后唯一能捞回「被回退抹掉的东西」的来源；备份时机与还原纪律见 证伪前拍改动前备份，还原后重跑全量。
2. **切块搬移先验切块完整性**：用 `text.find("class X:")` 一类锚点切块前，先确认切出的边界完整、后一块没被截半，确认后再写盘。切块算法 bug 的症状是判据大面积炸红而不是报错。
3. **正则改写前先想好退路**：批量替换不区分「这段代码的形状」，结构件（同步壳、装饰器、分支骨架）最容易一起被改没；一旦丢了，**直接重写整个文件**，不要继续打补丁——补丁叠补丁只会把原结构越补越远。同源教训见 自动修复要「动得可见」，门禁不该在检查途中改被检查的东西。
4. **出事后只回退动过的几行**：禁止 `git checkout <file>` / `git reset --hard` 这类整文件回退。
5. **改完先跑判据，再谈收尾**：写完代码不等于做完，判据跑绿才算；处于半成品状态就如实说「已写入但未验证」。
6. **恢复之后重跑全量**：只跑改动处附近的判据会漏掉「回退本身抹掉了别的东西」，全量是唯一能发现还原不完整的检查。

## Pre-conditions / inputs

- 一份拍在动手之前的备份
- 一条可跑的判据（否则第 5 步无从确认「该绿」）
- 结构类改动前先说清被搬代码的宿主对象是谁、边界在哪

## Failure modes / caveats

- **整文件回退抹掉同文件新改动**：不报错，最难发现。症状是「刚修好的几个缺陷集体消失」，事后只能从备份里逐行捞；在已经改坏之后才回退，等于用一次回退盖掉三处已完成修复。
- **切块边界不完整**：算法 bug 而非锚点写错，表现为某个方法只搬进一半、邻近类多出本不属于它的方法。
- **判据大面积炸红 ≠ 判据写错**：先当事故处理，再回头查判据；判据能红说明它真在起作用，见 把不变量写成会红的断言，并验证断言本身。
