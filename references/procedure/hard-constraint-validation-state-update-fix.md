# 硬约束校验与状态更新修复模式

**Trigger**：流程在阶段切换时被硬约束校验拦截，根因是校验时机过早——阶段模型尚未运行，状态对象全空。

## Steps

1. **调整执行顺序**：把「派发 → 更新状态 → 校验」改为「更新状态 → 校验 → 派发」，让校验拿到阶段模型跑过的结果。
2. **新增状态转换方法**：为状态对象（如 D-Card）补 `with_dcard()` 等不可变转换方法，使阶段模型返回值能写入状态而不破坏不可变约定。
3. **全空状态降级放行**：对尚未填充的状态实施降级（如放行 D-040 必填门），避免正常流程被预校验误杀。
4. **全仓搜索确认无运行时更新路径**：用 `grep` 搜索状态对象的运行时写入点，确认是否真的没有任何更新逻辑——这是定位此类缺陷的最快手段。

## Pre-conditions / inputs

- 阶段模型存在状态对象（如 D-Card），校验依赖其字段值。
- 校验环节在阶段模型运行之前触发。
- 派发环节本应更新状态，但实际上缺失该逻辑。

## Failure modes / caveats

- 只修时序不补更新逻辑，状态对象仍全空，后续阶段再次失败。
- 全空状态若不放行，修复后会从「被误拦截」变成「正常被拦截」，需区分预期拦截与历史误杀。
- 同型缺陷与 接线类缺陷只能靠「从外部观察真实装配根」的判据抓到 同源——参数在装配链中途被丢弃。
