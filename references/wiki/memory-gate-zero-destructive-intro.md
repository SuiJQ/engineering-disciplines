# 记忆门零破坏引入与上下文层触发度量

在存量系统里新增状态字段（如记忆门）时，采用「默认值 + 三处写入侧统一 setdefault」可实现零破坏性引入；触发度量从总量切换到上下文层可避免压缩器重复触发，但必须同步修复所有视图构造路径的字段透传，否则新状态会在压缩等操作中丢失。

## 零破坏引入模式

- **默认值前置**：在数据结构或类构造时为新增字段赋初值（记忆门用 `dict[RoleId, 记忆门类]` 初始化），使旧调用方拿到的对象天然带新字段。
- **三处写入侧 setdefault**：识别所有能新增角色状态的入口，统一 `setdefault(角色, 记忆门类())`，避免任何入口漏写导致键缺失。
- **范围收敛**：只动 `services/context/` 与编排核心，不动 `presentation/`、`adapters/`、`kernel/`、`tests/` 等下游；新字段天然出现在旧代码读到的对象里，下游无感。

## 触发度量切换：总量 → 上下文层

- **旧判据（总量 ≥ 阈值）**：压完后总量 = 阈值 + 记忆门 > 阈值，必然再次触发压缩，形成无意义循环。
- **新判据（上下文层 ≥ 配额）**：只计量上下文层自身，压缩器不动记忆门，新判据天然停止——与「压完仍触发」的旧行径形成对照。
- **等价区间**：记忆门为空时新旧判据等价；真实差异只在记忆门有内容时才出现，需要实测验证而非逻辑推演。

## 字段透传是同一类缺陷的两个面向

引入新状态后，**任何构造新视图的操作**都可能是字段丢失点。压缩器构造新视图时漏传记忆门即属此类——新字段虽已入状态，但在视图层被清空，表现为「导航标记消失」。这与 接线类缺陷只能靠「从外部观察真实装配根」的判据抓到 所说的「参数/模块在装配链中途被丢弃」同型，也与 判据查「结果怎么来的」不只查「结果长什么样」 所说的「只看终态被后续事件覆盖」同源。修复后须追加**证伪判据**（删透传 → 判据变红；还原 → 变绿）确保该路径不会再次静默失效。

## 触发条件切换的验证策略

- **诚实结论先行**：新度量在记忆门为空时与旧度量完全等价，实际差异只在记忆门有内容时才出现——不要拿等价区间的测试声称「已全面验证」。
- **需要压缩器新写法只是恒等变形**：旧行径（压完再压）与新行径（上下文层命中即停）在空记忆门下输出相同，但新度量才是正确终止条件。
- **压缩与截断的分工**：记忆门让压缩管只处理上下文层，属于 截断/压缩按 token 预算逐条扣减，装不下就如实说装不下 中「预算耗尽才截」原则的实例化——记忆门本身就是一份独立于预算的「保底材料」。
